۱. هدف کسب‌وکار (Business Purpose)
۱.۱. مسئله فعلی. مدیریت بازرسی تجهیزات ثابت (مخازن، خطوط لوله، مبدل‌ها، بویلرها) در بسیاری از پالایشگاه‌ها و مجتمع‌های پتروشیمی، هنوز بر پایه فواصل زمانی ثابت یا قضاوت فردی انجام می‌شود. این رویکرد دو پیامد دارد: از یک سو، تجهیزات کم‌ریسک بیش از حد بازرسی می‌شوند (هزینه اضافی)، و از سوی دیگر، مکانیزم‌های آسیب فعال در تجهیزات پرریسک ممکن است بین بازرسی‌ها از دید پنهان بمانند. همچنین، داده‌های بازرسی پراکنده و غیرقابل ردیابی، برنامه RBI را در برابر ممیزی آسیب‌پذیر می‌کند.

۱.۲. هدف. ساخت یک پلتفرم نرم‌افزاری RBI سازمانی که:

ریسک هر قطعه تجهیز را بر اساس احتمال خرابی (POF) و پیامد خرابی (COF) به صورت کمی و قابل دفاع رتبه‌بندی کند.

برنامه بازرسی را بر پایه ریسک، با فواصل و دامنه بهینه تولید کند.

قابلیت ممیزی کامل (Auditability) را تضمین کند؛ به گونه‌ای که یک ممیز مستقل بتواند کل تحلیل را از ورودی تا خروجی بازسازی کند.

داده‌های بازرسی و خوردگی را در یک سیستم مدیریت داده یکپارچه (IDMS) متمرکز کند.

۱.۳. ارزش کسب‌وکار مورد انتظار.

کاهش هزینه بازرسی از طریق حذف بازرسی‌های غیرضروری روی تجهیزات کم‌ریسک.

کاهش ریسک عملیاتی با تمرکز منابع بازرسی روی تجهیزات با بالاترین ریسک.

کاهش زمان و هزینه ممیزی‌های داخلی و ثالث از طریق شواهد دیجیتال و قابل ردیابی.

ایجاد پایه داده قابل اتکا برای تصمیم‌گیری‌های تعمیراتی و سرمایه‌ای (Turnaround Planning).

۴. نیازمندی‌های کسب‌وکار سطح بالا (Business Requirements)
توجه: این بخش «نیازمندی کسب‌وکار» است، نه «نیازمندی کارکردی سیستم». هر BR بیان می‌کند کسب‌وکار به چه قابلیتی نیاز دارد و چرا. تبدیل هر BR به نیازمندی کارکردی (FR) و غیرکارکردی (NFR) در سند SRS انجام خواهد شد.

BR-01: مدیریت یکپارچه داده‌های RBI
بیانیه: کسب‌وکار نیاز دارد تمام داده‌های موردنیاز برای یک تحلیل RBI (داده تجهیز، شرایط عملیاتی، مکانیزم‌های آسیب، تاریخچه بازرسی، و CMLها) در یک مخزن واحد و قابل ردیابی نگهداری شوند.

دلیل: API 580 صراحتاً «مدیریت داده» را به عنوان یکی از عناصر حداقلی برنامه RBI الزامی می‌کند. داده‌های پراکنده، پایه محاسبات را غیرقابل اعتماد می‌کند.

معیار پذیرش سطح کسب‌وکار: ۱۰۰٪ داده‌های ورودی یک تحلیل باید دارای منبع (Source)، تاریخ، و وضعیت کیفیت (Data Quality Status) باشند.

BR-02: شناسایی و مستندسازی مکانیزم‌های آسیب
بیانیه: سیستم باید بتواند مکانیزم‌های آسیب فعال و غیرفعال را برای هر جزء تجهیز شناسایی، مستند، و در صورت نیاز به تحلیل اضافه یا از آن حذف کند، با ثبت دلیل مهندسی برای هر تصمیم.

دلیل: API 580 «شناسایی مکانیزم آسیب» را عنصر حداقلی برنامه می‌داند. همچنین، ثبت مکانیزم‌های رد شده (Rejected) به همان اندازه مکانیزم‌های پذیرفته‌شده برای ممیزی اهمیت دارد.

معیار پذیرش سطح کسب‌وکار: برای هر جزء، فهرست مکانیزم‌های آسیب ارزیابی‌شده (اعم از پذیرفته یا رد شده) با دلیل مستند در دسترس ممیز باشد.

BR-03: موتور ارزیابی ریسک چندسطحی (POF × COF)
بیانیه: کسب‌وکار نیاز دارد ریسک هر قطعه تجهیز را با استفاده از احتمال خرابی (POF) و پیامد خرابی (COF) ارزیابی کند، و این ارزیابی باید در سه سطح کیفی، نیمه‌کمی، و کاملاً کمی (مطابق API 581) قابل اجرا باشد.

دلیل: API 580 اجرای هر سه سطح را مجاز می‌داند؛ انتخاب سطح باید بر اساس بلوغ داده‌ها باشد. اجرای تحلیل کمی بدون داده کافی، خروجی عددی گمراه‌کننده‌ای تولید می‌کند.

معیار پذیرش سطح کسب‌وکار: برای یک تجهیز نمونه با داده کامل، خروجی POF و COF باید با محاسبه دستی مبتنی بر جداول API 581 (حداقل برای مکانیزم نازک‌شدگی) مطابقت داشته باشد.

BR-04: تولید برنامه بازرسی مبتنی بر ریسک
بیانیه: سیستم باید بر اساس نتایج ارزیابی ریسک، فاصله بازرسی، دامنه بازرسی، و روش بازرسی پیشنهادی را برای هر CML تولید کند، و امکان بازبینی و تأیید انسانی (Override) را فراهم آورد.

دلیل: خروجی نهایی RBI، یک برنامه بازرسی قابل اجراست، نه صرفاً یک عدد ریسک. API 580 تأکید دارد که ریسک باید به تصمیم بازرسی قابل اجرا تبدیل شود.

معیار پذیرش سطح کسب‌وکار: برنامه تولیدشده باید برای هر CML شامل تاریخ بازرسی هدف، روش پیشنهادی، و سطح ریسک مرتبط باشد، و توسط مهندس بازرسی قابل تأیید یا اصلاح باشد.

BR-05: قابلیت ممیزی و بازسازی کامل تحلیل (Auditability)
بیانیه: برای هر تحلیل RBI، سیستم باید بتواند کل زنجیره تصمیم را بازسازی کند: داده‌های ورودی، نسخه موتور محاسباتی، فرضیات مهندسی اعمال‌شده، و مبنای هر خروجی.

دلیل: API RP 580 (Section 16) الزام می‌کند مستندسازی RBI به اندازه‌ای دقیق باشد که یک ممیز مستقل یا مرجع قانونی بتواند کل تحلیل و منطق رتبه‌بندی ریسک را حسابرسی و بازسازی کند. همچنین، نسخه موتور محاسباتی باید ثبت شود.

معیار پذیرش سطح کسب‌وکار: یک ممیز مستقل، با دسترسی به Audit Trail، بتواند بدون تماس با تحلیل‌گر اولیه، همان نتیجه ریسک را بازتولید کند.

BR-06: مدیریت چرخه بازرسی و بازخورد میدانی
بیانیه: کسب‌وکار نیاز دارد چرخه عمر یک بازرسی را مدیریت کند: از برنامه‌ریزی، اجرا، ثبت نتیجه، تا به‌روزرسانی تحلیل RBI بر اساس نتیجه واقعی.

دلیل: نقطه شکست رایج برنامه‌های RBI، فاصله بین «بازرسی برنامه‌ریزی‌شده» و «بازرسی واقعاً انجام‌شده» است. سیستم باید بتواند تأیید کند که بازرسی فرض‌شده در تحلیل، واقعاً با روش صحیح انجام شده است.

معیار پذیرش سطح کسب‌وکار: هر رکورد بازرسی باید به یک CML و یک تحلیل RBI مشخص متصل باشد، و نتیجه واقعی بازرسی باید در چرخه بعدی تحلیل تأثیر بگذارد.

BR-07: یکپارچه‌سازی با سیستم‌های سازمانی (CMMS/ERP)
بیانیه: سیستم RBI باید داده‌های اصلی تجهیزات را از CMMS/ERP (مانند SAP یا Maximo) دریافت کند و توصیه‌های بازرسی را به صورت اعلان یا دستورکار به آن سیستم بازگرداند.

دلیل: RBI نباید یک جزیره جدا باشد. یکپارچه‌سازی دوسویه از ورود مجدد داده جلوگیری می‌کند و اجرای برنامه را در گردش کار نگهداری سازمان ادغام می‌کند.

معیار پذیرش سطح کسب‌وکار: داده تجهیزات بین دو سیستم بدون ورود دستی همگام شود، و توصیه بازرسی تولیدشده در RBI به عنوان یک اعلان قابل پیگیری در CMMS ظاهر شود.

BR-08: گزارش‌دهی و داشبورد برای ذی‌نفعان چندگانه
بیانیه: سیستم باید دیدهای اطلاعاتی متفاوت برای نقش‌های مختلف فراهم کند: داشبورد تجمیعی برای مدیریت، ماتریس ریسک و جزئیات محاسبات برای مهندسی، و گزارش انطباق و Audit Trail برای ممیز.

دلیل: API 580 تأکید دارد گزارش‌دهی RBI باید متناسب با عمق فنی و اولویت‌های عملیاتی ذی‌نفعان مختلف تنظیم شود.

معیار پذیرش سطح کسب‌وکار: هر نقش، بدون نیاز به درخواست گزارش دستی، به دید اطلاعاتی متناسب با مسئولیت خود دسترسی داشته باشد.

BR-09: حاکمیت تغییر و مدیریت نسخه (Change Control & Versioning)
بیانیه: هر تغییر در داده‌های ورودی، فرضیات، یا نتایج تحلیل باید از طریق یک گردش کار قابل ردیابی ثبت شود، و نسخه‌های قبلی تحلیل برای مرجع حفظ شوند.

دلیل: بدون کنترل نسخه، Audit Trail بی‌معنا می‌شود. API 580 مستندسازی تغییرات و مبنای تصمیم را الزامی می‌کند. همچنین، سیستم‌های سازمانی RBI بر «حاکمیت تغییر» به عنوان یک ماژول پایه تأکید دارند.

معیار پذیرش سطح کسب‌وکار: برای هر تحلیل، حداقل دو نسخه (پیش و پس از یک تغییر مشخص) قابل مقایسه و بازبینی باشد.

BR-10: انطباق با استانداردهای مرجع و قابلیت جایگزینی موتور محاسباتی
بیانیه: سیستم باید محاسبات خود را بر پایه استانداردهای API 580/581 (و در صورت لزوم API 571 برای مکانیزم‌های آسیب) انجام دهد، و معماری آن باید به گونه‌ای باشد که موتور محاسباتی بدون تغییر در لایه‌های داده و رابط کاربری قابل ارتقا یا جایگزینی باشد.

دلیل: استانداردها بازنگری می‌شوند (مثلاً API 581 نسخه 2025). سیستم باید بتواند بدون بازنویسی کل نرم‌افزار، نسخه موتور را به‌روزرسانی کند. همچنین، برخی سازمان‌ها ممکن است بخواهند متدولوژی اختصاصی خود را اعمال کنند.

معیار پذیرش سطح کسب‌وکار: ارتقای نسخه موتور محاسباتی (مثلاً از API 581:2016 به 2025) نباید نیازمند تغییر در مدل داده یا رابط کاربری باشد.

۶. محدودیت‌ها و مفروضات (Constraints & Assumptions)
۶.۱. محدودیت‌ها.

سند مرجع اصلی، API RP 580 (4th Ed.) و API RP 581 (4th Ed.) است؛ هرگونه تغییر در استاندارد باید در نسخه‌های بعدی سند لحاظ شود.

داده‌های طراحی تجهیزات از سیستم‌های مهندسی موجود (مانند پایگاه داده مواد و طراحی) تأمین می‌شود؛ نرم‌افزار RBI مسئول تولید این داده‌ها نیست.

فاز اول بر تجهیزات ثابت تحت فشار متمرکز است؛ تجهیزات دوار خارج از محدوده‌اند.

۶.۲. مفروضات.

سازمان دارای یک RBI Basis مکتوب است که سطح تحلیل (کیفی/نیمه‌کمی/کمی)، ماتریس ریسک سازمانی، و اهداف ریسک را تعریف می‌کند.

داده‌های تاریخی بازرسی با کیفیت کافی برای شروع تحلیل کمی وجود دارد، یا سازمان آماده سرمایه‌گذاری در جمع‌آوری داده پایه (Baseline Data) است.

یک تیم مهندسی بازرسی با دانش API 580/581 برای پیکربندی و اعتبارسنجی سیستم در دسترس است.

۹. تحویل‌شدنی‌های این فاز و گام بعدی
۹.۱. تحویل‌شدنی این سند (BRS). این سند «قرارداد کسب‌وکار» برای دامنه، اهداف، و معیارهای پذیرش سطح بالا است. تأیید آن توسط ذی‌نفعان، پیش‌نیاز شروع فاز طراحی سیستم است.

۹.۲. گام بعدی: SRS. سند System Requirements Specification (SRS) بر پایه این BRS نوشته خواهد شد و شامل موارد زیر خواهد بود:

نیازمندی‌های کارکردی (FR) تفکیک‌شده برای هر BR (مثلاً FR برای «ایجاد CML»، «اجرای تحلیل POF»، «تولید برنامه بازرسی»).

مدل داده منطقی (موجودیت‌ها و روابط: Equipment، Component، CML، Inspection، DamageMechanism، AnalysisRun، AuditLog).

معماری سیستم (لایه‌ها، مؤلفه‌ها، نقاط یکپارچه‌سازی).

نیازمندی‌های غیرکارکردی فنی (کارایی، امنیت، دسترس‌پذیری).

محدوده نسخه اول (MVP) و نقشه راه فازهای بعدی.

۹.۳. شروع در Codespaces. پس از تأیید BRS و SRS، پیاده‌سازی در GitHub Codespaces با تعریف ساختار مخزن (Repository Structure)، انتخاب پشته فناوری (Technology Stack)، و ایجاد اسکلت پروژه آغاز می‌شود.
